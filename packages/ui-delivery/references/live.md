# Active browser feedback

Read for an ongoing browser-to-agent session. Use the existing project/profile and intended session in [interactive.md](interactive.md); preserve its answers, history and accepted decisions. Chat, delegated design, tiny edits and fully specified work keep their existing scope and question behavior.

## Establish the host path

Live mode requires an active agent servicing a foreground execution session. Start a bounded `listen` command with the host's yielding execution tool, retain its execution ID, and service it with that tool's continuation API. Use waits of at most 30 seconds so user messages and cancellation remain responsive. Verify that an explicitly submitted browser event reaches tool output and the same active agent can consume it before claiming host support. A running browser/server, filesystem watcher or canned consumer alone is insufficient. If yielding/continuation is unavailable, use the saved manual handoff and state that limit.

This package was verified with Codex `exec_command` returning `session_id`, then `write_stdin` returning the submission. Other hosts need their own trial. The listener cannot launch an agent, wake a closed conversation, or continue after the host stops it. The server may remain available for saving answers while the agent is disconnected.

## Connect, consume and return

Use `node scripts/ui-delivery.mjs help` from the resolved skill directory for exact flags. The server and listener are foreground processes; launch the server through a yielded tool session as well.

1. For tiny, fully specified or already answered work with no pending submission, implement and register its initially authorized result in manual mode before connecting; then use live mode for review feedback. Never invent an owner event to start a queue. Start or resume the intended session's server. Verify `/api/state` identifies the expected project/product and session, then give/open its exact loopback URL. `start` reopens saved state; `resume` is an explicit user transaction only for a paused session.
2. Run `connect --project DIR --session ID --consumer NAME --owner FILE`. Keep the private ownership receipt accessible to this agent. It contains the selected project/profile/session and a random capability; browser state never exposes that capability. Connection alone displays idle, not listening. Another consumer cannot connect until the owner disconnects or its two-minute lease expires.
3. Run `listen --project DIR --session ID --owner FILE --url URL --timeout-ms 30000` through a yielded foreground call. Keep servicing the execution ID. A timeout supplies no answer and performs no implementation; issue another bounded call while live mode is active. Never end the turn with a waiting message during an active listening session. The page reports waiting only while a serviced command holds a fresh lease.
4. On `status: submission`, read `checkpoint --project DIR --session ID --owner FILE --delivery ID`. Its handoff is the current authority, including missing answers, actual feedback, results and scoped acceptance. Compare the delivery's decision revision with the current one. If stale, reconcile any existing work, complete that delivery as `superseded`, and consume the newer one before dependent work. If required answers are missing or unsure, complete as `await-answers` and listen again; use only independent work meanwhile. Explicit delegation resolves only that question and requires a choice/rationale. Acceptance or resume events do not authorize extra edits. Rejection without specific changes needs clarification.
5. For a current implementation delivery, publish `work` with its fresh handoff revision and `--owner FILE --delivery ID`. Apply the actual answers/feedback within existing authorization. Use checkpoint before each dependent stage and at least once a minute during long work to renew ownership and detect newer submissions. A checkpoint is a point-in-time check; arbitrary file edits remain the agent's responsibility. If paused/disconnected/expired, stop dependent work and reconcile before retrying.
6. Inspect the real result, save a fresh pinned preview, and register `result` with the current revision and `--owner FILE --delivery ID`. Explain every answer and feedback resolution using the existing result schema. Registration rejects stale decisions/ownership. Return the real app URL where available; sandbox previews demonstrate rendering only.
7. Run `complete --project DIR --session ID --owner FILE --input FILE` with `{delivery_id, outcome:"result", result_id, message}` after registration. Other truthful outcomes are `await-answers`, `reviewed`, `superseded`, `blocked`, or `no-change`, with an explanation. Repeat the same completed receipt unchanged after a lost acknowledgement; conflicting retries fail. Then listen again so the user can inspect, submit feedback and see a revision without typing continue.

## Interruption and reconciliation

Deliveries coalesce pending explicit answer/feedback/acceptance/resume events, including submissions saved before listening. Agent work and result events never enter the queue. One consumer and one waiting command own a session at a time. Claims/completions live in the existing profile's optional `session.live` schema-1 extension, separate from decision history/revisions; connection updates cannot stale a browser answer or discard drafts.

Disconnect, crash, timeout and server restart retain uncompleted deliveries. A recovered delivery reports its original event IDs, revision, attempts and registered results. Before repeating effects, compare the current handoff, registered result and application files. Reuse a matching current result and acknowledge it rather than rebuild. Result registration is idempotent for a current delivery; durable acknowledgement does **not** make arbitrary application edits exactly-once. An edit completed before a crash without a registered result needs agent reconciliation, not blind replay. If a transaction left a lock, use the PID inspection procedure in [interactive.md](interactive.md).

`disconnect --project DIR --session ID --owner FILE` releases ownership and restores manual mode. Ctrl+C aborts only the current wait and leaves its lease idle; disconnect to release it immediately. A missed heartbeat becomes visibly stale after two minutes. `pause` or the browser's Pause session saves a cancellation, fences ownership and preserves drafts and pending submissions; it supplies no answer or acceptance. End dependent work. For later user-authorized resume, run `resume` (or use the browser), restart the server if needed, connect and listen. `stop --port PORT` ends only the selected local server and disconnects its consumer; saved decisions remain.

Report implementation evidence before inviting a real review loop. Make Pause session and chat exit clear. During that loop consume actual user submissions only, keep servicing the listener, and end on explicit pause/exit or a demonstrated host disconnection. Never invent feedback or acceptance to complete it. Whole-framework acceptance remains separate from any accepted fixture result.
